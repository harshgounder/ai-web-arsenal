## Decision tree

Machine readable at `trees/D12.json`. This is the rendered view.

- **Is the bug about order and timing, or about a rule?**
  - _why:_ Two different failures. Races break an assumption about concurrency. Logic breaks an assumption about sequence or value. The control differs.
- `Timing`
  - action: model the state transition, then send the pair together. sequential run first as the control
  - tools: `d12-turbo-intruder`, `d12-race-the-web`
  - oracle: `final state impossible sequentially, with the sequential control not reproducing`
- `A rule`
  - action: write the rule as the app states it, then find the sequence that satisfies every field check and violates the rule
  - tools: `d12-newman`, `d12-mitmproxy`
  - oracle: `an outcome the business rule forbids`
- `Retry and idempotency`
  - action: drop the response and resend. if the effect doubles, the operation is not idempotent
  - tools: `d12-mitmproxy`
  - oracle: `two effects from one intent`
- `Multi step approval`
  - action: change the object between steps. the approver sees one thing and applies another
  - tools: `d12-newman`
  - oracle: `applied object differs from the approved summary`

## Defense mirror

The other half of every row. An offensive entry with no matching detection and control is
incomplete, because the practical question is always against which defence.

| attack | detect | control | rule |
|---|---|---|---|
| race on a balance | two debits from one intent | atomic conditional update | concurrent write to one row |
| coupon or quota abuse | redemptions above the rule | server side counters, idempotency keys | quota exceeded per principal |
| negative quantity | sign not validated | range and sign checks per field | negative amount in a debit |
| sequence skip | workflow state jumped | transitions validated server side | state change without a transition event |
| retry duplication | same intent applied twice | idempotency key | duplicate operation within the window |
