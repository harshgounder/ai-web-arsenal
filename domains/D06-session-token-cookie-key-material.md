## Decision tree

Machine readable at `trees/D06.json`. This is the rendered view.

- **Where does the session state actually live?**
  - _why:_ Cookie, localStorage, bearer token, or a server side store. Each has a different failure mode and most people assume the cookie without checking.
- `Cookie`
  - action: read the attributes, then test rotation on login, logout, and privilege change
  - tools: `d06-mitmproxy`, `d06-curl`
  - oracle: `the same id used after rotation`
- `localStorage or sessionStorage`
  - action: check what the client can read and what an XSS would get. then check server side validation of that value
  - tools: `d06-rea-page`
  - oracle: `server accepts a client modified value`
- `Bearer token`
  - action: decode, then test validation: algorithm, audience, expiry, revocation
  - tools: `d06-jwt-tool`
  - oracle: `server accepts a token it should reject`
- `Server side store`
  - action: test idle and absolute timeout, concurrent sessions, and revocation on password change
  - tools: `d06-mitmproxy`
  - oracle: `session still valid after the event that should end it`

## Defense mirror

The other half of every row. An offensive entry with no matching detection and control is
incomplete, because the practical question is always against which defence.

| attack | detect | control | rule |
|---|---|---|---|
| session fixation | id unchanged after authentication | rotate on privilege change | session id continuity across login |
| cookie theft via XSS | theft pattern, then use from a new IP | HttpOnly, SameSite, short life | cookie use from a new source |
| token replay after logout | token still valid after logout | server side revocation list | token used after revocation |
| missing attributes | cookie without Secure, HttpOnly or SameSite | set them at issue | cookie attribute audit |
| concurrent session abuse | same session from many sources | bind to source, limit concurrency | session source spread |
