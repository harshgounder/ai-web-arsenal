## What this is, precisely

A list of tools is a directory. It tells you what exists and nothing about what to do, in what order,
what proves success, or what will stop you. Every web security collection on GitHub has the same shape
and the same failure: sorted by vulnerability class, no dates, no evidence standard, no procedure, links
that rot while the README implies completeness.

This repo is built on a different premise. **A completeness claim is worthless unless you define the
denominator.** So it defines one.

```
Set D   every factor that decides whether a web system can be made to do
        something its owners did not intend. 1,000 factors, 16 lenses.
Set A   what these repos actually contain, regenerated from disk on every run.
Set M   D minus A. The gap. Every element classified, every one graded.
```

Coverage is then a fraction with a stated denominator, not an adjective. That number is **39.7 percent**,
and it is published because publishing it is the point. A repo that claims completeness is making a
claim it cannot check. This one publishes its shortfall in the README and blocks its own release when
the shortfall and the prose disagree.

| lab | what it shows | the control that makes it evidence |
|---|---|---|
| `lab-01-race` | 24 parallel creates on a check-then-insert endpoint produced 24 records, 23 duplicates | sequential creates produced exactly one record and 23 rejections |
| `lab-02-jwt-alg` | an unsigned token declaring `alg: none` reached the admin panel | a wrong signature under HS256 was rejected 401, and the genuine user token was refused 403 |
| `lab-03-route-order` | `/%61dmin` and `/ADMIN` reached the admin handler past a guard that matched the raw path | the plain path is refused 401, an encoded public path behaves like its plain form, and the valid key is still accepted |
| `lab-04-cache-poison` | one request with a hostile `X-Forwarded-Host` was served to a second client that sent no header | the origin returns different bodies for different values, and a `no-store` endpoint is not cached |
| `lab-05-ssrf` | a fetch endpoint blocked the metadata host and still allowed loopback, returning an internal credential | the blocked scheme refused, the metadata host refused, and a missing internal path proving the request reached it |
| `lab-06-idor` | an endpoint authenticated the caller and never checked ownership, so each user read the other's note | no token refused, unknown id 404, and owners still able to read their own |

Both controls exist because a single positive is indistinguishable from a broken harness. In the first
case 23 duplicates could be a retry bug; in the second, a 200 could mean signatures are not checked at
all. `python3 scripts/observe.py --verify` replays both and fails if a verdict changed.

The shape of the table is the finding:

- The covered lenses are the ones where a tool exists that states its own oracle. Smuggling, cache,
  GraphQL, deserialisation, hash cracking, subdomain takeover. Tools carry procedures because they were
  built to be run.
- The three zeros are the three lenses no scanner can exist for: a speculative execution window, a
  support desk, and a disclosure deadline. Those need authored procedure and a lab.
- Money at 6 percent is the worst return per unit of real world impact in the table. Business logic is
  where loss actually lands.

## The ceiling

A coverage fraction is only half a claim. The other half is how much of the remainder is even
reachable, because a number that can never be improved is a different fact from one that is expensive.

The 603 uncovered factors are classified, generated into [`docs/CEILING.md`](docs/CEILING.md):

| class | meaning | cost | factors |
|---|---|---|---|
| I | derivable with noise, the mechanism is published | authoring only | **3** |
| II | inferable from structure, needs a probe | a lab and a target | **550** |
| III | genuinely unavailable, an internal fact | impossible from outside | **50** |

**The ceiling is 95.0 percent.** That is the share of Set D any collection could reach from outside,
given unlimited time. It is not a forecast of what this repo will reach.

The high ceiling is the finding, and it cuts against the usual story about this field. Almost nothing in
the denominator is secret. The constraint on completeness is effort and access to a lab, not hidden
knowledge. Fifty one factors are permanently out of reach, and twenty seven of those are about how one
organisation runs itself, which no external party can know.

Three consequences worth stating:

- **3 factors are reachable with no target and no permission.** 236 have been written across ten batches. Three survive, and they are the honest answer rather than a rounding error: QUIC stream reset, analytics pseudonym rejoin, and editor extension authority each need something this corpus does not have.
  statute and standards are published and this repo simply never wrote them down. That is the cheapest
  coverage in the project.
- **603 factors need a lab.** This is where the observed zero lives, and it is why the next phase exists.
- **Money has zero Class I factors.** Every one of L08's 58 remaining factors needs a running system,
  which is exactly why it sits at 6 percent despite being where most real loss happens.

So the honest ladder is three numbers, not one:

```
39.7%   covered today, 397 factors with a procedure and an oracle
34.6%   if every Class I factor were authored, which one person can do
95.0%   the ceiling, which needs about 60 labs and does not exist yet
 0.6%   observed, 6 factors, because exactly six labs exist
```

## Why it exists

Three questions a list cannot answer:

1. **What do I run, and how?** Every tool carries an install channel resolved against a real package
   manager, a verify command, a JSON output flag, and a one line agent usage note.
2. **What do I think, and in what order?** Every domain carries a machine readable decision tree.
3. **What will stop me, and what proves it?** Every domain carries a defence mirror, and every atlas
   pattern carries a counter and a negative control.

And one the whole field cannot answer: **how much of it is covered**. That is what the denominator is for.

## The denominator: sixteen lenses

Set D is not a list of vulnerabilities. It is the set of properties, mechanisms, constraints and actors
that decide whether one is possible. A pit stop is not 2.3 seconds; it is regulations, tyre chemistry,
aerodynamics, human motor learning, meteorology and game theory compressed into one moment. A web
compromise is the same shape: it is the convergence point of sixteen disciplines, and sorting attacks by
vulnerability class sorts one axis of a sixteen axis system.

| id | lens | what it owns | example factor |
|---|---|---|---|
| L01 | substrate | CPU, memory, allocator, collector, JIT, kernel boundary | `L01-008` JIT optimisation assumptions |
| L02 | network and transport | IP, TLS, HTTP/1.1, H2, H3, DNS, WebSocket, WebTransport | `L02-036` unkeyed header acceptance |
| L03 | protocol semantics | REST, GraphQL, gRPC, SOAP, JSON-RPC, MCP, SAML, OAuth | `L03-032` XML signature wrapping |
| L04 | frameworks and runtimes | routing, binding, serialisation, templating, defaults | `L04-030` host header trust |
| L05 | client and browser | DOM, engines, WASM, service workers, extensions, webviews | `L05-009` prototype pollution to gadget |
| L06 | identity and session | authn, authz, MFA, WebAuthn, SSO, tokens, impersonation | `L06-022` session termination completeness |
| L07 | data and storage | SQL, NoSQL, object, queue, cache, search, migrations | `L07-027` replica lag as an authz window |
| L08 | business logic and money | pricing, coupons, refunds, inventory, auctions, payouts | `L08-009` coupon scope enforcement |
| L09 | infrastructure and edge | CDN, proxy, WAF, gateway, serverless, container, IaC | `L09-031` metadata service reachability |

  "factors": [ "..." ]

## What a factor looks like

Every factor carries four things, because a factor you cannot test is a label rather than a factor.

```json
{
  "id": "L02-036",
  "name": "unkeyed header acceptance",
  "def": "whether a response varies on a header that is not in the cache key, which is the poisoning mechanism",
  "observable": "a response cached with a value derived from an unkeyed input",
  "evidence": "run"
}
```

- `def` says what the property is.
- `observable` says what you would look at to decide it.
- `evidence` is one of `source`, `paper`, `run`, `vendor`, so a reader knows what kind of claim stands
  behind it.

`scripts/validate-denominator.py` enforces all four on all 1,000, plus unique ids, lens prefixes, and
that no lens is empty. An unwritten lens reports as missing rather than as zero, because those are
different facts.

## What a coverage record looks like

The join is graded, and the grading is strict enough to be uncomfortable:

```
L0  absent      nothing in either repo addresses the factor
L1  named       a tool or entry mentions it, with no procedure and no oracle
L2  procedure   a procedure and an oracle, so a competent reader could test it
L3  observed    a lab here demonstrates it
```

**Only L2 and L3 count as coverage.** L1 is recorded because knowing a concept is named but not
operationalised is useful, and it is not counted.

```json
{
  "factor": "L02-036",
  "lens": "L02",
  "level": "L2",
  "covered_by": ["d10-wcvs", "d10-curl"],
  "basis": "entry",
  "note": "Unkeyed input is the poisoning mechanism, and curl is named as the way to read the cache headers that confirm a hit."
}
```

Every record names the artefact it relies on. `scripts/coverage.py --validate` resolves each cited id
against both repos and rejects any that does not exist. It rejected five ids that were invented during
authoring, which is the mechanism working rather than an embarrassment.

A record that says L0 with no artefact is also a claim, and it is the honest one for most of the table:

```json
{
  "factor": "L01-027",
  "lens": "L01",
  "level": "L0",
  "covered_by": [],
  "basis": "none",
  "note": "Nothing in either repo operationalises a substrate factor. This is the largest single gap in the project and it is stated rather than hidden."
}
```

## A worked example, end to end

Take cache poisoning, because it exercises the whole loop.

**Step one, define the factor.** `L02-036` is unkeyed header acceptance. The observable is a response
cached with a value derived from an input the cache does not key on.

**Step two, find the procedure.** `d10-wcvs` is in the corpus with preconditions and an oracle, so the
factor grades L2. The entry says what to send and what a hit looks like.

**Step three, prove it without fooling yourself.** A cache result is easy to fake: an intermediary may
have served you a stale copy, or the payload may have been normalised by the edge. So the proof needs a
negative control, which is a request with the same shape and the hostile value removed. If the response
still carries the injected value, the cache did not do what you thought.

**Step four, name what stops you.** The defence mirror for this class is in `data/domains/D10.json` under
`mirror`, with the control class and the defensive level. If a full page cache has a key including the
header, the technique is dead and the mirror says so.

**Step five, record what happened.** A coverage record at `L2` naming `d10-wcvs`, and none at `L3`
because no lab has run it here.

The whole loop is four data structures, all checkable:
`data/denominator/L02.json`, `data/domains/D10.json`, `data/coverage/coverage.jsonl`, `data/claims.yaml`.

## What a fresh clone can do

Tested, not assumed. A checkout with no companion repo beside it passes eight of ten gates and **skips
two with a stated reason**, rather than failing:

```
gates: 10  pass 8  fail 0  skip 2

Skipped gates could not run here. That is not the same as passing: it means part of this repo
was not checked. The usual cause is a missing companion repo.
```

An environment problem reported as a repository problem is the most expensive kind of false alarm,
because it teaches people to ignore the gate. So `scripts/preflight.py` checks the four things that are
actually environmental and prints the exact command for each:

```bash
python3 scripts/preflight.py
```

| check | needed for |
|---|---|
| python 3.10 or newer | everything |
| companion repo beside this one | pattern search, mutation generation, four claims |
| raw harvest in `raw/` | a from-scratch corpus rebuild only, not validation |
| `gh` authenticated | re-running capability mining only |

One dependency is outside both repos and is stated rather than hidden: the WSTG and ASVS taxonomy rows are
read from `~/web-universe-work/universe-nodes.json`, so the 624 of 706 figure cannot be rebuilt from this
repo alone. The committed `data/taxonomy-coverage.json` stands without it, and preflight reports the gap.

## Quickstart

Two commands to a working toolkit on Arch, CachyOS, EndeavourOS or Manjaro.

```bash
git clone https://github.com/harshgounder/ai-web-arsenal.git
cd ai-web-arsenal
bash bootstrap/00-prereqs.sh          # base-devel, git, AUR helper, uv
bash bootstrap/15-install-minimal.sh  # 13 tools
bash bootstrap/90-verify.sh           # proves every binary runs
```

Dry run first, if you prefer to see what it does:

```bash
DRY=1 bash bootstrap/15-install-minimal.sh
```

The installer refuses to run as root, never pipes curl to sh, and is idempotent. Every run logs to
`bootstrap/logs/`.

Then wire the extraction spine and follow [`BOOTSTRAP.md`](BOOTSTRAP.md) for the full bring-your-own-AI
setup: which model, which MCP servers, which skills, and the first fifteen minutes of prompts.

Verify the whole repository, not just the installs:

```bash
./scripts/gate.sh
```

## The method

```
capture -> inventory -> reverse artifacts -> hypotheses -> test -> prove -> critic
```

| step | what you do | pack |
|---|---|---|
| capture | record the traffic, the storage and the DOM before touching anything | `prompts/01-recon-capture.md` |
| inventory | enumerate what the application actually ships, not what it says | `prompts/02-bundle-teardown.md` |
| reverse | recover the serializer, the signing function, the route table | `prompts/02-bundle-teardown.md` |
| hypothesise | state what you think is broken and why, before testing | `prompts/03-hypothesis.md` |
| test | run the smallest action that distinguishes your hypothesis from it being false | `prompts/04-prove-it.md` |
| prove | confirm through a channel other than the one you attacked | `prompts/04-prove-it.md` |
| critic | have a second pass whose only job is to break your finding | `prompts/05-critic.md` |

The critic step is the one most work skips and the one that decides whether a finding survives a vendor's
response. A finding without a negative control is a hypothesis with a screenshot.

## What a row actually looks like

Every entry carries fields a list omits. This is D11's `clairvoyance` entry:

```json
{
  "name": "clairvoyance",
  "driver": { "install": "pipx:clairvoyance", "verify": "clairvoyance --help", "json": true },
  "atom": ["A01", "A08"],
  "preconditions": ["introspection disabled", "field suggestions enabled"],
  "oracle": ["schema_partial_recovery", "suggestion_error_differential"],
  "evades": ["F3"],
  "detected_by": ["field suggestion abuse pattern"],
  "procedure": [
    "confirm introspection is actually off with a direct query",
    "clairvoyance -o schema.json -w wordlist URL/graphql",
    "compare recovered fields to what the UI calls, the gap is the unauthorised surface"
  ]
}
```

The `procedure` field is what makes a row executable instead of descriptive. All 37 D11 entries have one.

Measured 2026-10-27, the mandatory-field rule is not met across the corpus: of 562 entries, 453 declare
preconditions (81 percent), 464 declare an oracle (83), 175 declare `evades` (39), and 135 declare what
detects them (30). Seven entries are deliberate pointers into the atlas and carry none by design. The
rest is real work, tracked in [`RECHECK.md`](RECHECK.md) and checked by claims `C053` to `C053d`.

## The range

Four labs, each a target this repo generates and attacks, each producing one observation. They exist
because `ESTABLISHED` means cited and nothing here could claim `OBSERVED` until something ran.

```bash
python3 scripts/observe.py            # runs every lab, records the verdicts
python3 scripts/observe.py --verify   # replays them, fails if a verdict changed
```

A lab is a `target.py` and a `probe.py`. The target is deliberately vulnerable in one specific way. The
probe runs the attack and at least one negative control, and it returns `INCONCLUSIVE` rather than
`OBSERVED` if any control is dirty. That last part matters: a lab whose control also shows the bug is
measuring its own harness.

| lab | the bug | why the control makes it evidence |
|---|---|---|
| `lab-01-race` | uniqueness checked in code, then inserted | sequential creates produce exactly one record |
| `lab-02-jwt-alg` | the verifier dispatches on the token's declared algorithm | wrong signature rejected 401, user token refused 403 |
| `lab-03-route-order` | the guard reads the raw path, the router decodes it | plain path 401, encoded public path behaves like its plain form |
| `lab-04-cache-poison` | a cache keyed on path alone, in front of a header reflection | reflection is header dependent, `no-store` is honoured |

`rea-ops/` is the other half of the same idea for extraction: code that reads an artefact the repo could
not previously read, with a fixture and a test, or it does not go in.

## The MCP server

An agent should not read 500 entries to find one. `mcps/arsenal-mcp.py` serves the same data as tools over
stdio, standard library only except for one optional import: `tools_for` and `claims` parse YAML and need
PyYAML, and without it those two say so while the other seven keep working. A tool that needs an install
to answer a question is worse than grep.

```json
{
  "mcpServers": {
    "arsenal": {
      "command": "python3",
      "args": ["${HOME}/ai-web-arsenal/mcps/arsenal-mcp.py"]
    }
  }
}
```

Nine tools:

| tool | answers |
|---|---|
| `search_entries` | which entries touch a term, and **whether each has an oracle**, so a caller can tell a procedure from a mention |
| `get_entry` | one entry complete, including preconditions, oracle, evades and driver |
| `search_patterns` | atlas patterns by title or target state, with status |
| `get_pattern` | one pattern with its counter and negative control |
| `coverage` | the grade for a factor, or a level summary for a lens, or the whole denominator |
| `gaps` | the classified gap: I derivable, II needs a lab, III unavailable |
| `tools_for` | manifest tools with the install channel that actually resolves |
| `domains` | the registry with entry counts |
| `claims` | what this repo asserts about itself, with the check behind each one |

`mcps/test-mcp.py` drives it over stdio the way a client would, and it is in the gate. It checks that
`search_entries` agrees with a direct disk read, that `coverage` returns the same grade as the ledger,
that a missing id returns an error payload rather than a crash, and that an unknown tool is a protocol
error. A server that starts is not a server that answers.

## Capability mining, and why the first answer was wrong

The third breadth engine asks the registries what exists for a job instead of trusting a list. It produced
the most instructive failure of the whole session.

**The first version was meaningless.** It searched `in:readme`, so the top web security candidates were
`public-apis`, `developer-roadmap`, `yt-dlp` and `ollama`, and it reported 82% of tools as new to the
lists. Reading the rows rather than trusting the output is the only reason that did not get published.

The funnel after two corrections:

| stage | count | what removed it |
|---|---|---|
| topic search hits | 222 | - |
| relevant to security | 139 | a vocabulary filter, because `topic:reverse-engineering` returns `gpt4free` and a visual novel translator |
| already known | 86 | 52 by repository slug, 9 by name, 25 by name containment |
| **genuinely new** | **53** | |

**53 tools across fourteen capability queries are absent from all nineteen curated lists.** The ones I
recognise as plainly real: SafeLine, OWASP MASTG, osv-scanner, FLARE-VM, lamda, reconFTW, nettacker,
afrog.

The third correction matters most. Matching only on repository URL reported `apktool`, MobSF and
ModSecurity as new, which they are not: they are present under another URL or another name. **An overlap
check that only looks one way measures its own index.** Name containment is what fixed it, and 25 of the
86 matches came from that alone.

```bash
python3 scripts/mine-capability.py     # 14 topic queries, then the funnel
python3 scripts/mine-capability.py --check
```

Nothing here is admitted to the corpus. `C119` enforces that every row stays `CANDIDATE`, and the
headline number is the new count, which measures what nineteen curated lists did not contain.

## The mutation engine

The second breadth engine, and the one with the most room to be dishonest, so it is built to be the least
interesting thing in the repo to inflate.

**2,399 candidate variants** derived from 150 patterns across six axes:

| axis | candidates | the question it asks |
|---|---|---|
| principal | 450 | the same action from a lower role, another tenant, or unauthenticated |
| encoding | 450 | the same value through a different encoding or case |
| context | 450 | the same value in a header, the path or a multipart part |
| timing | 449 | the same sequence parallel, staggered or replayed |
| protocol | 300 | the same action over HTTP/2 or grpc-web |
| state | 300 | the same action before commit or after a soft delete |

**Every one is `UNVERIFIED` and none of them counts as coverage.** `C116` enforces that each names what
would promote it, and `C117` enforces that no generated candidate enters the atlas. A generated variant
that was never run is a hypothesis with a plausible shape, and this repo has spent twenty rounds learning
what happens when hypotheses get counted as facts.

The generator skips any axis the source pattern already carries, so these are additions rather than
duplicates of hand written work. Each row states the premise, what changes, and the check that would
confirm it:

```json
{
  "id": "W01-0001.principal.lower_role",
  "from_pattern": "W01-0001",
  "axis": "principal",
  "premise": "as an authenticated principal with fewer rights",
  "check": "the action succeeds for a role that should not reach it",
  "status": "UNVERIFIED",
  "promote_when": "a run reproduces it with a negative control that shows the same procedure without the mutation has no effect"
}
```

It is a queue, not a corpus. The value is that a reviewer has 2,399 specific things to try instead of 150
to re-read.

## The advisory dataset

The first breadth engine. A curator cannot read thousands of advisories, but a machine can map them, and
the mapping is useful even when it is wrong as long as it is auditable.

**1,261 advisories** harvested from the OSV query API across 41 web significant packages in six
ecosystems. Scoping is a **selection made before the query**, not a keyword filter after it, because a
pipeline that pulls everything and filters afterwards produces a corpus whose size is mostly the filter's
false positive rate.

**993 mapped (78.7%), 268 unmapped (21.3%).** Of the mapped, 543 are high confidence (two or more distinct
patterns matched) and 450 medium.

| atom | advisories |
|---|---|
| A07 resource exhaustion | 270 |
| A01 interpreter confusion | 258 |
| A10 logic assumption | 207 |
| A02 trust boundary | 141 |
| A08 information exposure | 91 |
| A06 path and namespace | 82 |

Two properties make it auditable rather than magical:

- **every record carries the terms that matched**, so a reader can disagree with a classification without
  rerunning it (`C115` enforces this)
- **it is a separate dataset with its own counts** (`C114`), because mixing generated records with hand
  authored ones is how a size claim gets inflated. This repo made that mistake once with corpus rows and
  is not repeating it with advisories

The unmapped share measures the **classifier's recall, not the advisories' irrelevance**. Reading a sample
of the 268 finds real mechanisms the pattern table does not name yet, including "Improper Neutralization of
Input During Web Page Generation", which is CWE-79's formal name for XSS and was invisible to the first
pass until the word was added.

```bash
python3 scripts/harvest-osv.py     # 41 package queries, about 40 seconds
python3 scripts/map-advisories.py  # classify and report
```

## The counter layer

The defensive half, and the part that answers the other half of the brief: what will stop you, and what
does it miss. Fourteen control classes, generated into [`counters/COUNTERS.md`](counters/COUNTERS.md),
matching the ids the atlas uses so a pattern's `counter` field and a class record mean the same thing.

Each class states six things, and the pair that matters is the middle two:

| class | mechanism | **what it sees** | **what it structurally cannot see** |
|---|---|---|---|
| C01 | per object ownership check | caller and owner at the same layer | paths that fetch without calling the checked function |
| C07 | one parser for the whole path | the bytes it parsed | the other parser downstream, whose existence is the desync precondition |
| C09 | every varying input in the key | the key it built | inputs it did not model: a header it forwards, normalisation it applies after keying |
| C11 | append only logging with attribution | acts the application chose to log | acts through an unlogged path, or a principal fabricated upstream |

A control described only by what it stops is marketing. The blind spot column is the attack surface, and
the cost column says what using it will cost you: **C13 maintenance and process** is the cheapest class
for a patient attacker, because the bypass is waiting rather than requesting.

```bash
python3 scripts/render-counters.py --check
# 14 control classes checked, every field present
```

## The gate

A phase is done when the gate exits 0, not when the prose says so.

```bash
./scripts/gate.sh          # offline, about a minute
./scripts/gate.sh --full   # adds the network stage, the rebuild, and the denominator check
```

Real output:

```
ai-web-arsenal gate
===================

  PASS  install matrix is live
  PASS  doc numbers match disk
  PASS  prose claims hold
  PASS  regression tests
  PASS  domain invariants
  PASS  atlas pattern gate
  PASS  generators are deterministic
  PASS  denominator is complete
  PASS  coverage ledger is sound

gates: 9  pass 9  fail 0
```

What each one is:

| gate | what it refuses |
|---|---|
| install matrix is live | a package name that does not resolve |
| doc numbers match disk | a figure in prose that readme-stats no longer produces |
| prose claims hold | a claim in `data/claims.yaml` that stopped being true |
| regression tests | any of 21 known defects returning |
| domain invariants | an entry missing atom, oracle or driver, or an atom stored as a string |
| atlas pattern gate | a pattern missing its counter or negative control |
| generators are deterministic | a number that a fresh clone would not reproduce |
| denominator is complete | a lens that is unwritten, or a factor with no observable |
| coverage ledger is sound | a citation to an artefact that does not exist |

## Measuring the prose, and why the metric failed

Four rounds of hunting fiction in the documentation found four real defects, and the rate was not dropping.
So I tried to turn hunting into measurement: extract structural sentences, then ask whether any claim
covers each one.

```bash
python3 scripts/claim-coverage.py
```

The tool works. **Its number does not.** It reports 383 structural sentences, 109 with a plausible claim,
and 165 that contain a digit or a universal word but name no claim. Looking at those 165 finds mostly
narrative:

> Taken from the F1 pit stop plan on the desktop, because the shape of the problem is the same.

That is an explanation, not a claim, and it can never be checked. Automated sentence classification cannot
tell a claim from an explanation, and tuning the threshold until the number looked defensible would have
been the same failure this repo is built to catch, one level up.

So the number is reported as **an upper bound and not a defect count**, the file is written to
`data/claims-coverage.json` as a review order, and it is deliberately **not a gate**. A gate on a
miscalibrated metric is noise with authority.

What it did produce: three real claims that were in prose and in no ledger. The capability funnel's new
count, the topic pass rate, and the one external dependency. That is a fair return for a tool whose
headline number I do not trust.

## The claims ledger

45 claims, each a sentence in a document with a Python expression that decides whether it is still true.
It covers the facts with no stats key, the structural invariants, and **any superlative the documents make
about themselves**.

```yaml
- id: C053c
  statement: "135 of 475 entries declare what detects them, which is the weakest field in the repo"
  check: "sum(1 for e in entries() if e.get('detected_by')) == 135"
```

<!-- claim-ok: names the exact phrases the gate blocks, as documentation of the gate -->
A line that says this repo is the best, the most complete, or unlike everything else fails the gate
unless it carries an inline justification with a reason:

```markdown
<!-- claim-ok: quotes the request in order to reject it as unmeasurable -->
The ask was "the most complete in all of humanity".
```

That mechanism caught three of this repo's own overclaims while it was being built, including a sentence
claiming all 444 entries carried six fields when only 75 percent carried two of them.

## Defects found in this project

21 so far, all in [`RECHECK.md`](RECHECK.md) section 8, each with the lesson it produced. They share one
shape: a plausible artefact that nothing validated, wrong in the flattering direction.

| # | defect | what it taught |
|---|---|---|
| 1 | two recalled facts wrong, one repo called stale that was active, one called live that was archived | trust the API, never a summary page |
| 2 | link checker used HEAD, and real sites answer HEAD 404 with GET 200 | check how you check |
| 3 | classifier fell back to one class, so every unmatched counter became "authorisation" | a silent default is a claim |
| 4 | repository URLs invented, indistinguishable from the real ones | a URL not fetched is a hypothesis |
| 5 | a coverage metric measured its own scoring, giving 14 then 26 then 52 percent | when a metric needs three tries to look good, the metric is the problem |
| 6 | backlog quoted as 10,476, real 1,419 | counted the parser output, not the claim |
| 7 | corpus quoted as 24,759, real 21,384 after image and badge removal | an image is not an entry |
| 8 | name repair ran after its generator and was discarded, then the regex never matched | repairs belong inside the generator |
| 9 | row total quoted as a tool count, overstating tools by 2.4 times | a row is not a tool |
| 10 | 13 shields.io language badges shipped as tools | a filter matching one shape is a sample |
| 11 | a broken pacman repo turned 16 packaged tools into "unresolved" | in a lookup failure, ask which lookup |
| 12 | the identity line printed "+ residue" and hid 75 orphan rows in a word | name every term, sum them out loud |
| 13 | 687 rows held an owner/repo identifier in their url field | a locator is not a link |
| 14 | a pre-dedupe figure was printed as the promotable total | label the stage, not just the number |
| 15 | the README claimed 444 complete entries when 75 percent carried two fields | a field list is not a coverage claim |
| 16 | bootstrap held 14 scripts while the docs said 11 generated | a generated directory must own its contents |
| 17 | the REA backlog was stated as 12, the file names 10 | count the file, not the memory |
| 18 | the link check file had no generator at all | an artefact with no producer is a memory |
| 19 | seven entries stored a relative path in a url field | a pointer is not a link |
| 20 | D11 claimed WebSocket and SSE in its title with no such entry | a domain title is a claim |
| 21 | five artefact ids invented while authoring the coverage ledger | cite an id, then check it exists |

The standing rule that came out of these: **if a number cannot be regenerated from disk, it is not a
number, it is a memory.**

## How to add to this

Read [`AUTHORING.md`](AUTHORING.md). The short version:

1. Write `data/domains/DXX.json` with atoms, entries, tree, mirror and gaps.
2. Every entry needs `preconditions`, `oracle`, `evades`, `detected_by` and a `driver`.
3. If the technique exists in the atlas, do not restate it. Point at the wave file rather than at a
   pattern id, because that is the granularity the linkage actually uses (see the companion section).
4. Render with `scripts/render-domain.py`. Never hand write the generated file.
5. Map the new content into `data/coverage/` if it covers a factor that was absent.
6. Run `./scripts/gate.sh`. A claim that fails is a false statement, not a formatting problem.

## What this is not

- **Not complete.** 10.7 percent, stated above, with the table to prove it.
- **Not a lab.** Nothing here has been observed running. `OBSERVED` is 0 for a reason.
- **Not a scanner wrapper.** 1,419 candidates are indexed and not enriched. The enriched 444 are the
  ones with a procedure and an oracle.
- **Not authorisation.** Every pattern assumes written permission. The regulation lens exists partly
  because this repo has no answer for scope, and that gap is named rather than glossed.
- **Not neutral about evidence.** A finding without a negative control is not a finding, and a claim
  without a check does not ship.

## Companion repo

**[web-attack-atlas](https://github.com/harshgounder/web-attack-atlas)** holds the technique layer: 16
atoms, 150 patterns, preconditions, oracles, negative controls, mutations, counters and 13 control
classes. This repo holds tools, domains, corpus, install and the denominator.

**The join is at wave granularity, not pattern granularity, and that is measured rather than intended.**
Eight entries point into the atlas, one of them at a wave's `patterns.jsonl` and six at `QUEUE.json`, which
lists waves that are not built yet. **Zero of 562 entries reference a pattern id.** An earlier version of
this README said the join key was `entry_id`, which described an interface that was never used; the figure
is now generated by `readme-stats.py` and pinned by `C120`.
Neither restates the other.
